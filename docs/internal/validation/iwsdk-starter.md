# The Immersive Web SDK starter on the Mac

- **Question:** What does Meta's Immersive Web SDK starter bring when installed the way Halcyonic would vet it,
  and can a project made from it be type checked, built and served on the Mac with no network, from a config the
  project cannot change ([ADR 0037](../decisions/0037-new-vr-apps-start-from-a-host-vetted-web-starter.md))?
- **Date:** 2026-10-29.
- **Environment:** an Apple M5 Max, macOS 26.7; Node.js 24.15.0, npm 11.12.1; `@iwsdk/core` 1.0.1 and
  `@iwsdk/create` 1.0.1 (both 2026-10-01; npm's `latest` was the release candidate 1.1.0-rc.2 and was not used).
- **Method:** one download on the owner's yes (2026-10-29, private use), into a scratch folder, with npm given an
  empty user and global configuration, a cache of its own, `--ignore-scripts`, no audit or fund calls, and HTTP
  logging; `npm pack` for the create package's tarball, unpacked as data and never run. Then a test project from the
  template, type checked, built and served inside a Seatbelt profile that denies every outbound connection and
  allows writes only to a cache folder outside the project. Registry metadata was read the day before to plan the
  download.
- **Status:** installed and run on this Mac, as below. Not tried: a browser loading the page, the headset, WebXR.

| Licences | 53 MIT, 14 Apache-2.0, 6 pmndrs packages whose `LICENSE` is MIT, 3 BSD-3-Clause, 1 BSD-2-Clause, 1 ISC, 1 CC0-1.0, and `@drawcall/uikitml` 0.1.8 with none stated (a dependency of `@iwsdk/core`; no licence file in the package or its repository) |
| Install scripts | esbuild's postinstall and fsevents', present and not run; esbuild's binary comes in `@esbuild/darwin-arm64` |
| Not brought | Meta's `metavr` (not MIT; its postinstall downloads a binary and edits the shell's rc file), `@iwsdk/vite-plugin-dev` (sends telemetry through metavr, installs Playwright's Chromium at first use), `@iwsdk/reference` (an ONNX runtime and an embedding model) |

`@drawcall/uikitml` depends on `playwright` and `@sentry/node`; Playwright's npm package downloads no browser, and
Sentry is imported only by uikitml's command line `feedback` command, which nothing runs.

Meta's 1.0.1 starter pins `super-three` 0.181.0 and `@types/three` ^0.181.0, though its main branch had moved to
0.185. With 0.185, `tsc` failed on the template's own code: `@iwsdk/core` carries its own `@types/three` 0.181, and
two copies of the types do not mix.

## What the template needs

- `virtual:iwsdk-project` is generated by Meta's development plugin from `iwsdk.config.json`. The same module is
  a few lines over `@iwsdk/core/project`'s own `normalizeProjectWorldOptions`, as the plugin's source shows
  (`packages/vite-plugin-dev/src/index.ts`, read on GitHub's main branch). The plugin itself is not needed.
- The template's `tsconfig.json` and `vite-env.d.ts` name the plugin's types; a starter of Halcyonic's own declares
  the virtual module instead.
- The default scene loads three glTF models from `cdn.jsdelivr.net` (`@iwsdk/example-assets` 0.4.2) at run time, in
  the browser. A starter that must fetch nothing at run time leaves them out; its banner, panel and sound are local.

## Type check, build and serve with no network

| Step | Result |
| --- | --- |
| A connection to the registry from inside the profile | Refused (`curl` exit 6) |
| `tsc --noEmit` | Exit 0 in 0.8 s |
| `vite build`, host config, native config loader | Exit 0 in 8.1 s; main chunk 6.57 MB (1.69 MB gzip), uikitml's font chunks 0.5 to 0.7 MB each |
| `vite` serving on 127.0.0.1 | Ready in 0.5 s; the page answered 200 with the Content-Security-Policy header; the app's entry and the virtual module answered 200 |
| The project folder | No file changed |

Vite bundles a configuration file into `node_modules/.vite-temp` before loading it, even an `.mjs` one, which a
profile that keeps the dependencies read only refuses; `--configLoader native` loads it as it is.

## Controller models from the Mac

- **Question:** can a starter's controllers show their models with no network?
- **Date:** 2026-10-29.
- **Found in the installed `@iwsdk/xr-input` 1.0.1:** the button layouts are bundled
  (`dist/gamepad/generated-profiles.js`); only the models are fetched, from one constant,
  `DEFAULT_PROFILES_PATH = 'https://cdn.jsdelivr.net/npm/@webxr-input-profiles/assets@1.0/dist/profiles'`
  (`dist/gamepad/input-profiles.js`), with no option to change it. A controller's model is
  `<profile>/<left|right>.glb` of its first matching profile; a tracked hand's is `generic-hand/<left|right>.glb`
  (`dist/visual/adapter/base-visual-adapter.js`, `AnimatedHand.assetProfileId`).
- **Fetched, on the owner's yes (2026-10-29):** `@webxr-input-profiles/assets` 1.0.20 (MIT), the Quest 3's
  `meta-quest-touch-plus` and `meta-quest-touch-plus-v2` models, left and right (2,042,788 bytes in all), and its
  `LICENSE.md`, from jsDelivr; each size and SHA-256 equal to jsDelivr's published listing, recorded in
  `starters/iwsdk-vr/host/input-profiles.json`. On a second yes the same day, the `generic-hand` models, left and
  right (94,572 and 94,004 bytes), the same way; the package's `LICENSE.md` covers them.
- **Tried on this Mac:** a fresh starter project built and served with the host config, network denied, the models in
  a host folder: the build and the dev server's pre-bundled code no longer name the CDN (Vite's source map of the
  pre-bundled module still holds the original text); the build carries the six models byte for byte and the notice;
  the server answers a listed model as `model/gltf-binary` and 404 to an unlisted model, `..` paths and the package's
  own layout. Not tried: a browser loading a model, the headset.

## Playing on a laptop and in VR (M1.8a)

- **Question:** what does SDK 1.0.1 give for playing in a desktop browser without a headset and without its
  emulator, and does the starter's input layer turn a mouse and keyboard into the game's input?
- **Date:** 2026-10-29.
- **Read in the installed `@iwsdk/core` 1.0.1:**

| What | Where | On a laptop |
| --- | --- | --- |
| Rendering outside XR | `World.create` draws to the page's canvas until a session starts | yes |
| Mouse into the scene | `input.canvasPointerEvents` (the starter sets it) forwards the canvas's pointer events into the scene with `@pmndrs/pointer-events`' `forwardHtmlEvents`; off during a session unless `activeDuringXR` | yes |
| `Hovered` and `Pressed` | `InputSystem` adds them on `pointerenter` and `pointerdown` of each `RayInteractable`, the same listeners a controller's or hand's ray uses | one path for mouse and rays |
| Keyboard, browser gamepad, actions | `input.keyboard`, `input.browserGamepads`, `input.actions` with bindings from keyboard, browser gamepad and XR gamepad | yes |
| Default bindings | `xr` (thumbsticks to move and turn, A to jump) on by default; `browser-first-person` adds W A S D and the arrows, Space, and a browser gamepad | `interaction.select` is declared with no binding |
| Looking with the mouse | none (no pointer lock or drag to look in the package) | missing |
| VR entry | `xr.offer` calls `navigator.xr.offerSession` when the browser has it; the template's panel button calls `launchXR` | a desktop browser has neither, so the button cannot start a session there |
| The emulator | IWER through `@iwsdk/vite-plugin-dev`, not in the vetted set | not used |

- **Tried on this Mac:** the template with the layer and one test box (not in the template), served by the host
  config with the network denied, opened at `?check` in headless Chrome inside the check's sandbox and driven over
  the DevTools protocol: the layer reported `laptop`, the box's screen point, then one `mouse` after a real press
  and release on it, the box left the view after a 200-pixel drag on empty space, and one `key` after Space. The
  panel showed the laptop line and no VR button. `tsc` passed on the template. The turned view held for the half
  second the probe waited; longer was not measured. Not tried: controllers, hands and touch on the headset, and the
  Quest Browser's own VR offer.

## The check opens the page (M1.5b)

- **Question:** does a passed type check and build mean the game runs, and can the host tell?
- **Date:** 2026-10-29.
- **Found with six agent-built games** (SH, `qwen3.6:35b-a3b-nvfp4` through Codex 0.157.0), each opened for 10 seconds
  in the check's headless Chrome: three threw uncaught exceptions in their own code (a white screen, or no canvas)
  although two had passed the type check and build; three threw nothing but showed nothing of the game from the laptop
  camera. Every project, the starter included, had yoga-layout's inlined WASM refused by the preview's policy
  (`connect-src 'self'`); allowing `data:` removed that refusal, and the six games' own exceptions remained.
- **Drawn:** sharp edges outside the welcome panel in a picture at 3 s and at 10 s. The empty starter has 0, one small
  box about 2,700, the clean whack-a-mole run about 7,450. More than 200 counts as drawn. It passed one run whose
  picture showed floating spheres rather than a whack-a-mole: drawn is not working.
- **Tried on this Mac** (the check against SH's installed set and Chrome, opt-in tests in `check.test.ts`): the empty
  starter type checks, builds and throws nothing but is not drawn; a box in front of the camera is drawn; an exception
  thrown by the page is caught. One SH game threw on Vite's development server but not as a production build; the
  check opens the build, which is what the headset is served.
- **Not tried:** the headset, a click or trigger reaching the game.

## The check presses the game and offers VR to a stand-in (M1.8b)

- **Question:** can the host tell that a new game takes a mouse and keyboard on a laptop, and that it offers VR,
  without trusting what the game's own page says?
- **Date:** 2026-10-30.
- **Laptop step,** in the same load after the 10 s watch, opened with `?check` so the starter's layer sets its hook:
  the host reads the hook's targets and counts (bounded, timed out, shape-checked: `reported`), then for up to three
  targets takes a control pair of pictures 1.1 s apart with no input, presses with a real mouse over the DevTools
  protocol (move, press, release), and takes a picture 1.1 s after the one before the press. Space and E follow.
- **Thresholds and why:** a pixel has changed when any channel moved by more than 40 of 255, the same step the edge
  count uses, so compression and anti-aliasing noise do not count. The screen changed after a press when more than
  0.5% of its pixels did (5,120 of Chrome's 1,280 by 800, about a 72-pixel square, the size of a small object reacting
  near the camera), and only when the control pair changed at most 0.1% (about 1,000 pixels: a still scene's noise,
  never an object moving). Above 0.1% in the control the scene moves on its own, and the change is unknown, never a
  yes. These are design choices checked on the cases below, not measured on agent-built games yet.
- **Laptop ready:** the layer reports the mouse reached, the project's `src/play-input.ts` and
  `src/play-input-core.ts` are byte for byte the template's, and the screen is observed changed. The first two are
  what the page says; only the last is the host's own, and only it may be worded as checked by the computer.
- **VR-entry step:** a second load with a stand-in `navigator.xr` installed before the page's scripts, reporting
  through a binding with a random name that it takes into its closure and deletes from the global object. The starter's
  World offers `immersive-vr` as it loads (`xr.offer: 'always'`), so offered means the game kept that; it is offered
  to a stand-in on the Mac, never shown on a headset.
- **Tried on this Mac** (opt-in tests in `check.test.ts`): the empty starter has nothing to press and is offered VR;
  a 0.9 m box the game listens to, which grows and turns blue on a click, is reached, observed changed and offered, so
  ready; the same game with its layer changed is not laptop ready; with a cube spinning beside it the change is
  unknown; a page that calls every binding-shaped function and every global that differs from a fresh frame's, in its
  own window and in a frame, with its World not offering VR, is not offered (with the delete removed, the same page
  is offered, so the test can see a leak).
- **Not tried:** agent-built games against these thresholds; a key a game reads other than Space and E; the headset.

## A press seen against a twin, for scenes that move (M1.8g)

- **Question:** can the host tell a game's response to a press from the scene's own motion, without trusting the page?
- **Date:** 2026-10-30.
- **Found on SH's four saved games** with M1.8b's step (no model): none laptop ready. One still game's click changed
  nothing (its moles never pop); one had its layer changed by its agent; the two animated ones read unknown, their
  scenes changing 0.26 to 0.95% with no input, and near the pressed point a press changed no more than the scene did
  (glimmer 10.9% against 13.8%). A second load pictured at the same moment differs as much, since moles pop at random.
  The step also read a target's point before its 1.1 s control pair, so a moving mole was missed; it now reads the
  point right before the press.
- **Twin replay:** before the page runs, the host injects a clock that moves only 1/60 s per frame and only to frames
  the host steps to (300, 303, 306, 360), seeding `Math.random`, `crypto.getRandomValues` and `crypto.randomUUID`. Two
  no-input loads of glimmer, glimmer2 and the still game matched 0.00% at frames 300 and 360. A press on a mole that
  was up differed from its twin by 0.13 to 0.19% at frame 360; a press on one that was down, or on the still game,
  by 0.00% (glimmer2 counts a hit only on a mole that is up). DevTools virtual time was tried first: in headless=new
  the game's frame loop did not run between budgets, so a press never reached it.
- **Thresholds and why:** a response is seen when a press that reached the layer changes the end frame from the
  twin's by more than 0.05% (about 420 pixels of 1,280 by 657: under a third of the smallest hit seen), and only when
  the press run and its twin match within 0.01% at the frame before input; otherwise the page has a source of time or
  chance the clock does not hold, and the response is unknown. Up to five targets, each in a load of its own.
- **Two controls (AUDIT M18G-M1, 2026-10-30):** matching before input does not show the twin holds at the frame
  compared. A page that starts something late on a time the clock does not hold (a CSS animation at frame 330, a
  worker's clock used only later, an asset that finishes loading late) differs between loads with no input at all,
  which a single twin would read as a response. The step now loads the page twice with no input, the second after the
  presses (AUDIT M18G-S1); the two must match within 0.01% at frame 300 and at frame 360, or the response is unknown. A press seen is loaded once more, and must end
  within 0.01% of its first run. A second control samples load-to-load change; it does not prove there is none: a
  page whose late change lands alike in two loads and otherwise in a third could still pass, and is unknown to us.
- **Time (AUDIT M18G-M2, M18G-S2):** a step to a frame counted 50 ms waits rather than time, and on a throttled Mac one
  step ran about 906 s. The whole twin step now has three minutes by the wall clock, of which the last 25 s are kept
  for a load told to stop to end (a DevTools answer's 20 s, Chrome's 3 s); past it the step reads unknown and its Chrome
  is stopped before the check goes on. A fixed 30 s per step (first amend) also cut off pages whose frames had slowed on
  a busy Mac; instead the page must reach a further frame at least every 10 s, and the clock reports every frame.
- **The null under load (M1.8g-b):** on 2026-10-30 a full e2e run beside other suites (load about 23 to 26 on 18 cores)
  read two moving scenes unknown that read seen when the Mac was quiet, with no reason recorded; three reruns at load 20
  to 30 read seen. Two causes were possible and neither was shown: a picture taken before the held frame was drawn, and
  the 30 s step limit. Pictures of a held frame are now taken again until two in a row match, and an unknown read
  records its reason (`response_unknown`).
- **Loaded before stepping (M1.8g-c):** with the reason recorded, a moving scene whose click does nothing read
  `controls_differ` once in two runs beside a looping `pnpm check` (load 15 to 42): its two no-input loads differed. A
  twin load held the clock at frame 0 for a fixed 3 s; it now holds it until Chrome reports the document loaded and no
  request has been in flight or begun for 1 s (Page and Network domains, observed in the host), for at most the 10 s
  stall limit, after which it steps anyway and a later change shows as a mismatch.
- **Tried on this Mac** (opt-in tests in `check.test.ts`): a box that answers a click beside a spinning cube is seen
  and ready; the same scene whose click does nothing is not; a page that steps itself with synthetic F24 keys and
  calls every binding-shaped global gets the same verdict; a cube turned by a worker's own clock reads unknown; a still
  scene that starts a CSS animation at frame 330 in sixteen squares, each at a phase drawn from a blob URL's random id,
  with a click that changes nothing, reads unknown on 3 of 3 runs, and seen and ready on 2 of 2 with the single twin
  (one square alone once ended alike in two loads, so the test uses sixteen); a page that hangs only under the twin's
  clock reads unknown once the step's time (8 s in the test) is spent, its Chrome's browser process exited and no twin
  process left within 5 s, on 4 of 4 runs (an earlier run that looked at once found one process of it still exiting).
- **Not tried:** agent-built games through the whole check with the twin; a game with late-loading assets.

## No service worker on a preview's origin (AUDIT M16A-C1)

- **Question:** can a game register a service worker on a preview's origin, which later projects on the same port share?
- **Date:** 2026-10-30.
- **Found:** with the host as it was, a page of the starter registered `./sw.js` from its own `public/` in the check's
  headless Chrome (156.0.8078.76) over http://127.0.0.1: registration resolved (opt-in test, failing first).
- **Now:** the host's preview and dev servers answer 404 to any request with the `Service-Worker` header, which the
  Service Workers specification puts on every worker script fetch (W3C Service Workers editor's draft, read
  2026-10-30: the Update algorithm's fetch hook appends `Service-Worker`/`script` to the request); the same page's
  registration is refused.
- **Not tried:** the Quest Browser (the headset is away). A worker registered before this change stays: when an update
  fetch fails, the same algorithm removes the registration only if it has no worker yet. Clearing storage on a reused
  port, which would remove it, is the next unit.

## Consequences

- A starter made from these pinned versions builds and serves on the Mac with no network and no install script.
- What runs on the Mac at preview is Vite and TypeScript from the vetted set, configured by the host; the project's
  own code only runs in the browser.
- Open: whether Quest Browser treats `http://127.0.0.1` (never `localhost`) through `adb reverse` as a secure context
  for WebXR ([quest-browser-preview.md](quest-browser-preview.md)), and
  the uikitml licence, which the owner decides before anything containing it is published.
