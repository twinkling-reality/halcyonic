# A picture or a file with an instruction (parity A4)

- **Question:** what does each runtime Halcyonic drives accept besides text with an instruction, and do the local
  models see a picture?
- **Date:** 2026-11-11.
- **Versions:**
  - `codex-cli` 0.157.0 (app-server, stable surface);
  - `@opencode/cli` 2.0.18 (v2 HTTP);
  - `@anthropic-ai/claude-agent-sdk` 0.3.283 with its bundled CLI, and `@anthropic-ai/sdk` 0.128.0;
  - Ollama 0.40.15 on this Mac.
- **Method:**
  - Codex: its own protocol, generated by `codex app-server generate-ts` and `generate-json-schema` from 0.157.0
    at the 2026-09-27 smoke run ([codex-capabilities.md](codex-capabilities.md)).
  - OpenCode: the OpenAPI document 2.0.18 served at the 2026-09-26 smoke run
    ([opencode-capabilities.md](opencode-capabilities.md)).
  - Claude Code: the Agent SDK's type definitions, plus a runtime probe of its bundled CLI against a fake Messages
    API on loopback.
  - Local models: `POST /api/show` on loopback Ollama (no generation).
  - Then runtime probes of the pinned Codex and OpenCode binaries, each against its end to end suite's fake
    provider ([Runtime probes](#runtime-probes)).
- **Status:**
  - What each interface accepts is verified, from its own schema or types.
  - Each of the three runtimes passing a picture to its provider is verified, on a fake provider.
  - Not verified: any model answering about a picture.

## What each runtime accepts

**Codex.**
- `UserInput` items, the same in `turn/start` and `turn/steer` (`TurnStartParams.input`, `TurnSteerParams.input`):
  - `{type: "text", text, text_elements}`;
  - `{type: "image", url | fileId, detail?}`;
  - `{type: "localImage", path, detail?}`;
  - `{type: "audio", url}` and `{type: "localAudio", path}`;
  - `{type: "skill", name, path}` and `{type: "mention", name, path}`.
- `detail` is `auto`, `low`, `high` or `original`.
- `model/list` entries carry `inputModalities` (`text`, `image`, `audio`), so a model says whether it takes a picture.

**OpenCode.**
- `POST /api/session/{id}/prompt` takes `{text, files?: FileAttachment[], ...}`. An attachment is
  `{uri, name?, description?, mention?}`, with no bytes or media type on input.
- The stored attachment holds `data` (base64) and `mime`, so the server resolves the `uri`. It takes `file://` and
  `data:` URIs and refuses a bare path ([Runtime probes](#runtime-probes)).
- A model's `capabilities.input` lists what it takes.

**Claude Code.**
- `SDKUserMessage.message` is an Anthropic `MessageParam`, whose content blocks include:
  - an image: `{type: "image", source: base64 jpeg/png/gif/webp | url | file}`;
  - a document: a base64 PDF, plain text, a URL PDF or a file id.
- **The probe** (bundled CLI, fake Messages API on loopback, a dummy key, a trap for any other traffic):
  - a base64 PNG block reached the API byte for byte;
  - a URL image block reached it as a URL, and the CLI did not fetch it;
  - nothing left loopback.

**Local models.** `POST /api/show` lists `vision` among the capabilities of every model Halcyonic checks, and of
the companion's:
- `muse-glimmer:30b-mlx`
- `qwen3.6:35b-a3b-nvfp4`
- `qwen3.8:27b-nvfp4`
- `qwen3.5:9b`

Whether one sees a picture through Ollama's OpenAI-compatible endpoint, as Codex and OpenCode reach it, needs a
generation; it was not run.

## What Halcyonic carries today
- `execution.start` (`instruction`), `execution.send_instruction` (`text`) and `execution.created` carry text alone,
  at most 32,000 characters.
- `StartExecutionRequest.instruction` and `sendInstruction`'s `text` are strings.
- No `RuntimeCapabilities` entry names attachments. Each adapter sends text only:
  - Codex: `[textInput(text)]`;
  - OpenCode: `{text}` and `{text, delivery: "steer"}`;
  - Claude Code: `[{type: "text", text}]`.
- OpenCode's gate in front of Ollama passes the request's `messages` on whole and caps a body at 8 MiB, so an inline
  picture under that would pass it (from the code; no picture was sent).

## Runtime probes
Run on 2026-11-11, after the reads above.

**The pinned binaries.** Downloaded fresh from the public npm registry with `--ignore-scripts`, outside the owner's
data folder. Each binary's SHA-256 equals the repository's own pin (`apps/control-plane/src/pins.ts`):
- `@opencode/cli@2.0.18`, about 176 MB on disk: `6759c7f86f807d63d3984ca1970f9fa663ee303a35bb344eb223c71e200a96bf`;
- `@openai/codex@0.157.0`, about 325 MB on disk: `ad0be20d04e2ba6146ecdb51d7f8b7b0fe15420a15dc9b0057518d858f1f3714`.

**The picture.** A 32 by 32 PNG drawn for the probe: a red square, a blue square and a green bar on white. Nothing
real.

**Codex 0.157.0.**
- Setup: a bare app-server client in the e2e suite's sandbox, with the suite's fake Responses provider recording
  every request.
- `turn/start` with `[{type: "text"}, {type: "localImage", path: <the PNG in the project>}]` was accepted.
- The turn completed. The provider's `POST /v1/responses` body held one `input_image` whose `image_url` is
  `data:image/png;base64,...`: Codex read the picture from the path and sent it inline.
- Nothing left loopback.
- `model/list` here lists the built-in catalog, where models carry `inputModalities: ["text", "image"]`.

**OpenCode 2.0.18.**
- Setup: a bare `opencode serve` in the e2e suite's sandbox, with the suite's fake OpenAI-compatible provider.
- On `POST /api/session/{id}/prompt`:
  - `files: [{uri: "file://<the PNG>"}]` was accepted (200);
  - a `data:image/png;base64,...` URI was accepted (200);
  - a bare path was refused with 400 `InvalidRequestError`, "Invalid attachment URI".
- In both accepted cases the provider's chat completion request held the picture as an `image_url` with the PNG's
  data URL.
- The model list gives each model's `capabilities.input`: the fake OpenAI-compatible model `["text", "image"]`, a
  model discovered through the Ollama provider `["text"]`.

## Can the Mac take a picture of what a project looks like now?
- **Already built, for the check:**
  - The check opens the built project in Halcyonic's pinned, sandboxed headless browser (chrome-headless-shell,
    through the launcher).
  - It takes PNG pictures over DevTools (`Page.captureScreenshot`, 1280 by 800) at 3 s and 10 s, and a no-input
    frame for the drawn comparison.
  - Each is kept in the check's own folder with its SHA-256 (`preview/check.ts`).
- **What that is:** a picture of the checked build at the time of the check. It is neither the preview the person
  is looking at now, nor what Play in Headset shows in Quest Browser.
- **A picture of the running preview now** would need a capture step of its own:
  - open the project's running preview on loopback in the same sandboxed browser;
  - take one `Page.captureScreenshot`;
  - keep it with its SHA-256;
  - attach it as any picture is attached.
- **What the Mac cannot take:** what the headset itself shows, the person's view or the room around them. That
  would be the headset's own capture.
